# 학습 대상 객체와 데이터 준비 기준

현재 Webots 월드와 `config/object_classes.json`을 기준으로 한 YOLO26 학습 계획입니다. **신규 클래스 학습 6종 + 기존 클래스 보강 4종 = 최종 탐지 클래스 10종**으로 구성합니다. 이 문서는 학습 대상과 준비 기준을 정리하며, 학습된 가중치나 학습 완료 결과를 포함하지 않습니다.

## 1. 무엇을 학습해야 하나

ID와 클래스 이름의 기준은 [object_classes.json](../config/object_classes.json)입니다. 아래 ID는 프로젝트 라벨 ID이며 COCO ID와 다릅니다. 기존 데이터와의 호환을 위해 순서를 바꾸지 않습니다.

| ID | 클래스 | 대상과 라벨 범위 | 기본 COCO 모델과의 관계 | 필요한 작업 |
| --- | --- | --- | --- | --- |
| 0 | `bench` | 벤치의 좌판·등받이·다리를 포함한 한 개체 | `bench` 존재 | 현재 월드의 목재·금속 벤치 외형과 시점 보강 |
| 1 | `traffic_cone` | 교통 콘과 받침대 전체 | 해당 클래스 없음 | 신규 클래스 학습 |
| 2 | `pedestrian` | 걸어가는 사람의 보이는 신체·의복 전체 | `person`을 현재 어댑터가 매핑 | 보행 자세·옆모습·가림·시뮬레이터 인물 외형 보강 |
| 3 | `signboard` | 보행로 위 독립형 입간판의 판·프레임·받침 | 해당 클래스 없음 | 신규 클래스 학습; 건물 벽 간판과 구분 |
| 4 | `bollard` | 낮은 말뚝의 몸체·반사띠·밑받침 | 해당 클래스 없음 | 신규 클래스 학습; 먼 거리에서 작은 대상 수집 |
| 5 | `pole` | 가로등의 세로 기둥·밑받침 | 해당 클래스 없음 | 신규 클래스 학습; 머리 위 가로등 조명·가로 팔은 제외 |
| 6 | `barrier` | 공사 펜스 한 개의 판·망·지지대·발 | 해당 클래스 없음 | 신규 클래스 학습; 기준 거리와 우회 월드의 서로 다른 펜스 포함 |
| 7 | `car` | 주차·주행 차량의 차체·바퀴 전체 | `car` 존재 | 현재 차량 외형 재학습; 이동 여부는 탐지 클래스와 별개 |
| 8 | `planter` | 보행 공간을 막는 융기된 화단의 구조물과 그 안의 식재 | 동일 클래스 없음 | 신규 클래스 학습; COCO `potted plant`와 일괄 매핑하지 않음 |
| 9 | `traffic_light` | 보행 신호등의 신호 표시부·하우징 | `traffic light`를 현재 어댑터가 매핑 | 보행 신호등 외형·작은 ROI·역광 조건 보강; 지주 제외 |

기본 체크포인트의 COCO 클래스는 [Ultralytics 공식 클래스 목록](https://github.com/ultralytics/ultralytics/blob/main/ultralytics/cfg/datasets/coco.yaml)을 기준으로 대조했습니다. `stop sign`은 입간판이 아니며, `potted plant`도 보행 장애물인 화단과 범위가 다릅니다. 클래스 이름을 설정에 추가하는 것만으로 모델이 해당 객체를 탐지하게 되지는 않습니다.

위 bbox 범위는 **수동 검수·학습 데이터의 통일 기준**입니다. Webots recognition의 자동 bbox가 이 기준과 항상 일치하는 것은 아니므로 그대로 정답으로 확정하지 않습니다. 예를 들어 현재 `pole` recognition 대상은 세로 기둥이며, 신호등 지주 전체를 `traffic_light`로 라벨링하면 이 기준과 달라집니다.

## 2. 먼저 진행할 순서와 수집 시나리오

아래 순서는 보행 장애물과 교통 시연을 우선하는 프로젝트 제안입니다. 측정된 위험도 순위나 성능 순위가 아닙니다.

| 단계 | 우선 대상 | 수집할 시나리오 | 확인할 어려움 |
| --- | --- | --- | --- |
| 1. 핵심 보행 장애물 | `bollard`, `pole`, `traffic_cone`, `barrier`, `signboard` | `occluded_sign`, `slender_pole`, `construction_passage`, `residential_detour`, `station_access_detour` | 작은 크기, 일부 가림, 얇은 물체, 배경과 비슷한 색, 펜스의 빈 영역 |
| 2. 횡단보도 | `car`, `traffic_light`, `pedestrian` + 별도 신호 상태 판정 | `signalized_crossing`, `crossing_pedestrian`, `station_access_detour` | 주행 차량의 앞·옆·뒷모습, 먼 신호등, 보행자 교차, 빨강·초록·소등 |
| 3. 환경 보강 | `planter`, `bench`와 전체 클래스 재검증 | `courtyard_detour`, `residential_detour`, `urban_baseline` | 큰 화단, 식재에 가려진 경계, 벤치와 펜스의 오인식 |

수집 우선순위와 최종 모델의 클래스 수는 별개입니다. 최종 모델에는 10종을 모두 포함하고, 영상 속 대상 클래스 전체를 라벨링합니다. 예를 들어 펜스를 수집하는 영상에 사람이 함께 보이면 사람도 라벨링해야 합니다.

`driveway_transition`의 경계석·보도 단차·점자블록·포장 변화는 현재 10종 탐지 라벨에 포함되지 않습니다. 향후 단차·보행 가능 영역 인식으로 확장할 대상이며, 객체 탐지 학습이나 스테레오 깊이만으로 이미 처리된다고 가정하지 않습니다. 도로·횡단보도·나무·건물·출입구도 현재 탐지 클래스 밖입니다. 목적지 도착은 시나리오 좌표로 판정합니다.

## 3. 신호등은 위치 탐지와 색상 판정을 나눠 준비

현재 `traffic_light`는 신호 표시부의 위치를 찾는 클래스입니다. COCO `traffic light` 출력 자체는 빨간불·초록불 또는 보행 신호 여부를 알려주지 않습니다. **현재 빨간불 대기·초록불 안내는 `scenario_script` 출처이며 영상 기반 색상 판정은 아직 구현하지 않았습니다.**

후속 구현은 기존 10종 탐지를 유지하고 `traffic_light` ROI에 별도 상태 판정 모듈을 연결하는 방식을 우선안으로 둡니다.

| ROI 상태 라벨 | 의미 | 필요한 데이터 |
| --- | --- | --- |
| `red` | 보행 빨간불 | 밝기·거리·시점이 다른 빨간 신호 |
| `green` | 보행 초록불 | 같은 조건의 초록 신호와 전환 장면 |
| `unknown` | 색을 판단할 수 없음 | 소등, 심한 가림, 너무 작은 ROI, 반사·과노출 |

이 상태 라벨은 현재 탐지 클래스 ID 0–9에 추가된 클래스가 아닙니다. ROI 분류기·색상 규칙 중 어떤 방식을 사용할지는 후속 구현에서 정합니다. 별도 메타데이터에 프레임 시각, 신호등 bbox/ID, 상태 라벨을 보관하고, 시뮬레이터 신호 상태는 **학습·평가 정답으로만** 사용합니다. 추론에서는 이미지로 상태를 판단해야 합니다.

초록불 판정과 차량의 정지·횡단 구간 비움 판정도 구분합니다. 차량의 주행 여부는 한 장의 `car` bbox로 결정할 수 없으므로 추적·시간 정보 등을 이용한 후속 판단이 필요합니다. 깜빡임이나 여러 방향의 신호등을 넣는 확장에서는 시간 시퀀스와 보행자에게 해당하는 신호등 선택도 별도로 검증합니다.

## 4. 현재 실행에서 확인한 학습 공백

2026-11-14에 기본 `yolo26n.pt`, confidence 0.35, 640px 설정으로 전체 10개 시나리오를 실행했습니다.

- 모두 경로 진행과 영상·탐지·깊이 파이프라인 연결 검사를 완료했습니다.
- 실행 로그에 출력된 프로젝트 클래스는 `bench`, `pedestrian`, `traffic_light`였습니다.
- `traffic_cone`, `signboard`, `bollard`, `pole`, `barrier`, `planter`, `car`는 해당 실행 로그에서 출력되지 않았습니다. 신규 클래스 학습과 차량 외형 보강이 필요한 근거입니다.
- `bench`·`pedestrian`·`traffic_light`도 출력됐다는 사실만으로 정탐이나 충분한 성능을 입증하지 않습니다. 배경을 잘못 분류한 경우가 있는지 프레임별 정답 매칭으로 확인해야 합니다.

이는 실행 점검 기록입니다. 정답과 예측을 매칭해 계산한 클래스별 precision/recall이 없으므로 **정확도·미검출률·학습 완료 결과로 해석하지 않습니다.** 시나리오 전환 경계의 수신 메시지도 포함될 수 있어 개별 구간의 출력 목록을 정탐 목록으로 사용하지 않습니다. 원본 로그와 집계는 로컬 `webots/logs/all_scenarios_latest.json` 및 그 파일의 `report_dir`에 보관하며 Git에는 넣지 않습니다.

## 5. 데이터 수집과 라벨 검수

현재 수집 도구는 실행 중인 Webots의 동기 좌우 RGB와 좌측 recognition bbox를 저장합니다.

```bash
# 터미널 1: 원하는 시나리오 실행
./scripts/run.sh --pipeline baseline --scenario occluded_sign

# 터미널 2: 좌우 영상과 자동 라벨 초안 수집
source scripts/env.sh
"$CV_PYTHON" webots/scripts/capture_dataset.py --count 100 --interval 0.5
```

결과는 `datasets/sidewalk/<수집시각>/images`, `right_images`, `labels`, `metadata`에 저장됩니다. `--count 100`은 도구 사용 예시이며 클래스당 충분한 학습 수량을 뜻하지 않습니다. 유한 경로가 반복되므로 같은 장면의 중복이 쌓이지 않도록 확인합니다.

**현재 자동 라벨은 완성된 학습 데이터가 아닙니다.**

- `build_mission_worlds.py`의 신호등은 recognition용 `model`이 없는 개별 도형으로 생성됩니다. 따라서 현재 `capture_dataset.py`는 신호등 bbox나 신호 색 상태를 자동 생성하지 못합니다. 수동 라벨링 또는 월드의 recognition 대상 등록·신호 메타데이터 수집 기능이 필요합니다.
- 화단 중 `MISSION_PLANTER`만 `planter` recognition 대상으로 등록되어 있습니다. `SIDE_PLANTER`, `PLANTER_NORTH`, `PLANTER_EAST`와 기준 거리의 배경 화분은 자동 라벨에서 빠질 수 있습니다. 위 클래스 정의에 해당하는 가시 개체를 모두 검수·보완합니다.
- 다른 물체도 recognition 등록 여부, 가림, 화면 밖 잘림과 bbox 범위를 확인합니다. 누락된 대상이 있는 영상을 빈 라벨의 배경 이미지로 쓰지 않습니다.
- 한 물체에 bbox 하나를 지정하고, 보이는 부분을 기준으로 이미지 경계에 맞춰 자릅니다. 심한 가림으로 종류를 정할 수 없는 예시는 억지로 정답을 붙이지 말고 검수 대상으로 분리합니다.
- 펜스의 틈·화단의 식재·얇은 기둥 주변 배경은 bbox 내부에 섞입니다. 객체 탐지 정답이 좋아져도 거리 추정의 표면 선택 문제는 별도로 남습니다.
- detector는 `/assistive/stereo/left/image_rect`에서 추론합니다. 수집 도구는 `image_raw`와 해당 좌표의 자동 라벨을 저장합니다. 현재처럼 왜곡이 없는 평행 카메라에서 좌표가 일치하는지 확인하고, 리그·보정을 변경하면 영상을 정류하면서 bbox도 함께 변환하거나 정류 영상에 다시 라벨링합니다.
- 오른쪽 영상은 깊이 추정·동기 검증용입니다. 좌측 bbox를 오른쪽 영상의 정답으로 복사하지 않습니다.

각 클래스는 근거리·중거리·원거리, 정면·측면, 가림 유무, 화면 중앙·가장자리, 밝음·그림자, 재질·색·배치 변형을 포함하도록 수집합니다. 현재 기본 월드는 다양성이 제한되어 있으므로 반복 캡처만으로 일반화 데이터가 준비됐다고 보지 않습니다. 실제 카메라 적용 전에는 사용 권한이 있는 실제 보행 영상도 별도 수집·검증합니다.

## 6. 데이터 분리와 학습 연결

객체 탐지는 **좌측 이미지 + YOLO bbox 라벨**로 학습하고, 거리·방위각·시계 방향은 기존 스테레오 모듈에서 계산합니다. 두 카메라 RGB를 일반 YOLO26 입력 하나로 합치거나 거리·시계 방향을 객체 클래스로 만들지 않습니다.

최종 탐지 모델은 위 순서 그대로 10종으로 준비합니다. `data.yaml`의 `names` 예시는 다음과 같습니다. `path`는 실제 준비한 데이터셋 루트로 바꿉니다.

```yaml
path: /absolute/path/to/datasets/assistive_objects
train: images/train
val: images/val
test: images/test
names:
  0: bench
  1: traffic_cone
  2: pedestrian
  3: signboard
  4: bollard
  5: pole
  6: barrier
  7: car
  8: planter
  9: traffic_light
```

라벨은 같은 stem의 `labels/train`, `labels/val`, `labels/test`에 둡니다. 각 줄은 `class_id cx cy width height`이며 bbox 좌표는 영상 크기로 정규화합니다. 수집 원본 디렉터리를 바로 학습용 분할로 사용하는 대신 검수 후 이 구조로 정리합니다.

프레임 무작위 분할은 피하고 수집 세션·경로·배치·조명 변형 단위로 train/val/test를 분리합니다. 같은 경로의 반복 주행과 매우 비슷한 인접 프레임은 한 split에 묶고, 좌우 쌍도 함께 묶습니다. 각 split의 클래스 분포를 확인하며, 한 월드에만 존재하는 객체는 해당 월드의 독립 변형을 추가해야 세 split에서 평가할 수 있습니다.

학습은 준비한 10종 라벨로 COCO 사전학습 YOLO26을 fine-tuning하는 후속 작업입니다. API와 라벨 형식은 [공식 YOLO26 문서](https://docs.ultralytics.com/models/yolo26/) 및 [데이터셋 형식](https://docs.ultralytics.com/datasets/detect/)을 따릅니다. 현재 저장소는 이 문서 추가로 학습을 실행하거나 기본 가중치를 교체하지 않습니다.

학습 후 `models/`에 체크포인트를 두고 `config/pipelines/yolo26.json`의 `detector.weights`를 바꿉니다. `model.names`, `class_map`, `class_allowlist`와 프로젝트 이름이 일치하는지 확인합니다. `car`는 이동·주차를 모두 포함하지만 현재 한국어 catalog 표현은 “주차된 차”이므로, 주행 차량까지 안내하는 모델 연결 시 “차량” 등 중립 표현으로 별도 갱신해야 합니다.

## 7. 학습 후 검증할 항목

| 항목 | 기록할 결과 |
| --- | --- |
| 탐지 | 클래스별 precision/recall, mAP, 혼동 행렬, 거리·가림·bbox 크기별 미검출 |
| 깊이 | 정탐에 대한 유효 깊이 비율과 거리 오차; 미검출과 깊이 실패를 분리 |
| 방향 | 보행자 기준 방위각 오차와 시계 방향 구간 오분류 |
| 신호 | 빨강·초록·unknown 혼동 행렬, 빨강을 초록으로 판단한 경우, 전환 지연 |
| 시간·안내 | 촬영부터 안내까지 지연, 반복 안내, 잘못된 클래스의 음성 출력 |
| 통합 | 10개 시나리오 재실행과 독립된 실제 영상 평가 |

시뮬레이터 좌표·신호 상태는 평가 정답으로만 읽습니다. 모델 미검출이나 스테레오 실패를 정답값으로 채우지 않습니다. 승인 기준의 수치와 평가 데이터 규모는 데이터 준비 후 별도로 정하며, 현재 실행 완료 기록을 탐지 성능 합격으로 사용하지 않습니다.
